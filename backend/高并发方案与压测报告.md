# 天水流域生态环境监管平台：高并发方案与压测报告

## 1. 交付范围与结论

本次改造对象是“遥感影像生态指数计算”的任务提交链路，不把 HTTP 受理性能误写成 GeoTIFF 栅格计算性能。接口现在只创建持久化任务并尝试投递，返回 `202 Accepted`；Rasterio/GDAL/RSEI 的重计算由 Celery Worker 独立执行。

已完成一次真实 HTTP 压测：临时压测账号先通过真实 Session/CSRF 登录，再通过本机 Nginx 向 Django 接口发送 300 次、32 并发、同一 `X-Idempotency-Key` 的请求。300 次均返回 `202`，PostgreSQL 实际只创建 1 条 `ProcessingTask`，响应中只出现 1 个任务 ID，压测判定通过。

最终机器可读结果保存在 `backend/benchmark_submission_postgresql_300x32_pass.json`，由仓库内的 `benchmark_concurrency` 管理命令生成。

## 2. 实际架构

```text
Vue（每次业务提交带 X-Idempotency-Key）
            |
            v
Nginx（提交入口限流/连接保护；地图瓦片、静态和媒体不受该限流）
            |
            v
Django + DRF
  ├─ ProcessingTask：幂等键、请求指纹、活跃指纹、优先级、持久化 outbox 状态
  ├─ 数据库 UNIQUE(active_fingerprint)：跨 Web 实例的 single-flight 仲裁
  └─ 202 返回
            |
            v
Redis Broker / Celery 队列（geo.high / geo.default / geo.low）
            |
            v
Celery Worker（Linux prefork；Windows threads） -> Rasterio / GDAL / GeoServer
```

### 幂等与跨实例去重

- `X-Idempotency-Key` 合法长度为 8–128。相同键、相同影像/指数/优先级返回原任务；相同键但参数不同返回 HTTP `409`。
- `request_fingerprint` 包含影像、规范化（排序去重）指数集合、用户和优先级，用于判定同键参数冲突。
- `active_fingerprint` 只包含同一业务计算维度（影像、指数集合、用户），并由数据库唯一约束保证同时只能有一条活跃任务。该约束才是多 Web 实例下的最终裁决，不依赖进程内锁。
- 任务完成、失败或取消时清空 `active_fingerprint`；取消接口为 `POST /api/v1/environment/processing-tasks/{id}/cancel/`。实测取消后可用新幂等键创建新的任务。

### 可靠投递与任务状态

- 创建任务先落库：记录 `celery_task_id`、`queue_name`、`priority`、`dispatch_status`、`dispatch_attempts`、`dispatching_at` 和 `last_dispatch_error`。
- 投递状态是持久化 outbox：`pending -> dispatching -> dispatched/failed`。投递失败不删除任务；`python manage.py dispatch_pending_tasks --limit 100` 会补投 `pending`、`failed`，以及超时未完成认领的 `dispatching` 记录。
- Celery 使用确定性的 task id（等于 `ProcessingTask.id`），并启用持久消息、`acks_late`、worker 丢失退回队列、`prefetch=1`、25 分钟软超时、30 分钟硬超时。其语义是 **at-least-once**，因此 GIS 任务必须保持可重入，不能假设绝对的 exactly-once 消费。
- 优先级：`high -> geo.high (9)`、`normal -> geo.default (5)`、`low -> geo.low (1)`。

## 3. 部署参数

### Django / PostgreSQL

生产配置 `tianshuipy.settings_postgresql` 已支持：`CONN_MAX_AGE`（默认 300 秒）、`CONN_HEALTH_CHECKS=True`、`DB_CONNECT_TIMEOUT`（默认 5 秒）。生产库应使用 PostgreSQL（GIS 数据需要空间查询时使用 PostGIS），并执行全部迁移。

### Celery

Windows 演示环境使用：

```powershell
python -m celery -A tianshuipy worker -l info --pool=threads --concurrency=4 --queues=geo.high,geo.default,geo.low -Ofair
```

Linux 生产环境使用 `prefork`，GIS Worker 的初始并发建议取物理 CPU 核数或其 1/2，并按可用内存下调；每个栅格计算进程可能占用数 GB 内存，不能只按 HTTP 并发数盲目放大：

```bash
celery -A tianshuipy worker -l info --pool=prefork --concurrency=<CPU核数或内存核定值> \
  --queues=geo.high,geo.default,geo.low -Ofair
```

### Nginx

- `worker_processes auto`、`worker_connections 4096`、后端 upstream keepalive 64。
- 仅生态指数提交入口限流：每 IP 100 req/s，突发 200，提交连接上限 50；一般 API 仅连接保护 100。
- `/media/`、Vue 静态资源、GeoServer OWS 与 WMS/WFS API 代理不会被提交限流误伤。
- `client_max_body_size 10g`；上传/长请求的连接、发送、读取超时均为 10 分钟。

确保 Nginx 已加载 `deployment/nginx.conf`，另开终端执行：

```powershell
conda activate ts
cd D:\Zhangyong\Agents\tianshui_projectSU\backend
python manage.py benchmark_concurrency --base-url http://127.0.0.1:8081 --requests 300 --concurrency 32 --authenticated --report-file .\benchmark_submission_postgresql_300x32_pass.json
```

压测命令使用真实 HTTP、共享幂等键，并自动创建占位影像、任务与临时压测账号。`--authenticated` 会通过实际登录接口获取 Session/CSRF；它检查 202 数、数据库创建数及返回任务 ID 数，任一项不符合“300 / 1 / 1”即以非零状态退出。通过后任务会被标记为已取消并释放活跃锁；Worker 消费到该消息时会在 GIS 计算前安全忽略，避免为清理测试数据而制造 Broker 孤儿消息。

Broker 短暂故障后的补投：

```powershell
python manage.py dispatch_pending_tasks --limit 100 --stale-seconds 300
```

## 6. 风险边界与下一步

本报告的 155.61 RPS 是 **任务提交控制面** 指标，绝不是“每秒完成 155.61 景 GeoTIFF/RSEI”。本次实测已覆盖 PostgreSQL、Redis、Nginx、真实认证写请求和单 Web 实例，但尚未覆盖多 Web 实例、Linux prefork Worker 或栅格计算本身。

要开展端到端栅格压测，需提供：

1. 可合法用于测试的真实 GeoTIFF 样本及预期输出口径；RSEI 至少需要已校准的可见光/NIR/SWIR 与可靠热红外/LST 数据，建议按小、中、大三种文件量级准备多景样本。
2. Linux 目标机或容器规格（CPU、内存、磁盘类型/剩余空间），以及 PostgreSQL/PostGIS 与 Redis 的连接信息或部署权限。
3. GeoServer 的数据目录/工作区权限和性能监控口径（队列等待、单景耗时、成功率、内存峰值、I/O、发布耗时）。

拿到这些后应单独压测：队列等待时间、每景端到端完成时间、并行 Worker 数下的完成率与资源曲线，并用实际完成景数/小时或景数/天作为“栅格计算吞吐”指标。

## 9. 容量阶梯压测与推荐配置

### 方法与口径

所有档位均使用同一份真实 449.9MB Landsat 9 七波段输入；每个任务创建独立 `RemoteSensingImage` 数据库记录，因此其任务指纹不同，不会被幂等 single-flight 合并。没有复制或伪造像元数据。每轮均经过 Nginx、真实登录后的 Django API、PostgreSQL 任务记录、Redis、Celery threads Worker、Rasterio/GDAL 计算、GeoTIFF 写盘及 EcologicalIndex 落库；测试结束后由报告枚举精确的临时记录/结果目录并清理，JSON/CSV 原始指标与基准输入保留。

时延分位数使用 nearest-rank：小样本中 P95/P99 取最慢任务，避免被向下取整误写成 P50。CPU/RSS 为 Celery Worker 主进程及其子进程合计峰值；系统可用内存取压测期最低值。磁盘为 D: SATA HDD，采集到的是已用空间变化，未采集 IOPS，因此只能据时延和输出写盘量提示 I/O 风险，不能将其写成已证明的 IOPS 瓶颈。

### 结论、瓶颈与配置

- **NDVI：推荐并发 4，已验证安全上限为 8。** 4 并发取得全矩阵最高吞吐 11.681 tasks/min；提升到 8 虽然未 OOM，但吞吐反降 18.1%，P50 时延由 16.73s 增至 35.89s。因此 8 仅能表述为“在本数据集上实测通过”，不应作为生产推荐值。
- **RSEI：交互/稳态推荐并发 2，批处理可采用并发 4；已验证安全上限为 4。** 4 并发全成功并将吞吐从 1.664 提到 2.092 tasks/min（+25.7%），但 P50 时延由 68.28s 升至 106.32s（+55.7%），RSS 从 21.21GB 增至 37.89GB。没有执行 RSEI 并发 8，故不能宣称其安全上限超过 4。
- **实测瓶颈判断：** Redis 没有积压、数据库连接稳定且无投递/计算失败，二者不是本轮限制因素；GeoServer 不在该计算任务的处理路径中，未参与本轮瓶颈判定。NDVI 8 并发时 CPU 仅约 8.24 个逻辑核而单景时延明显恶化，结合每景 261MB 的 HDD 结果落盘，说明瓶颈更可能是 GDAL/Rasterio 全幅数组、内存带宽与 SATA HDD 并发 I/O 的组合，尚需 PerfMon/IOPS 才能分离归因。RSEI 的 PCA 与五文件写盘使该问题更明显。
- **已实施队列隔离：** RSEI 分量集合（greenness/wetness/dryness/heat）现在自动路由到 `geo.heavy`；轻量 NDVI/NDWI/NDBI 保持 `geo.high`、`geo.default`、`geo.low` 优先级队列。Windows 当前建议单独运行轻量 Worker `--pool=threads --concurrency=4 --queues=geo.high,geo.default,geo.low -Ofair`，重型 Worker `--pool=threads --concurrency=2 --queues=geo.heavy -Ofair`。这两个 Worker **同时混跑**尚未压测，故是基于隔离目标的部署起点而非混合负载实测容量；Linux 应改为 prefork 并重新做相同矩阵验证。
